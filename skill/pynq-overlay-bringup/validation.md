# PYNQ Overlay 启动与板端排障：验证记录

## RED：历史失败基线

**场景**：完整系统已经取得位流，整机 setup WNS 为 +0.045 ns，独立 CNN 测试也有正确输出，但首次板端控制访问无响应。

**当时覆盖缺口**：独立测试台主动提供了正确 reset，没有覆盖真实系统中 `proc_sys_reset` 的生成和连接。若只看“位流存在、时序通过、独立核仿真正确”，容易重复下载位流或过早把问题归因于 DMA／板卡失联。

**后续真实反馈**：HWH、实际生成 VHDL 和 BD 一致表明低有效 `aux_reset_in` 被常量 0 长期置为有效复位。修复后使用 metadata、load、control 分阶段入口，控制阶段实际读取 ABI、输入词数、时钟和 DMA 状态并完成 `PHASE_PASS`。

**由此形成的测试要求**：一个有效的排障 Skill 必须同时做到：

1. 检查实际生成系统的复位极性和常量，而非只验证独立核；
2. 将元数据、位流下载、首次控制读和 DMA 分开，前一层未通过不得进入下一层；
3. 在危险调用前后持久记录，不能以 Python 超时冒充 AXI 防死锁；
4. 权限、环境、CMA 和硬件协议问题必须分层，不得用一个“设备异常”概括。

来源：`HISTORICAL_ARTIFACT`，Round40／41 及发布包 `board/results/golden/`。这不是开发阶段原始 Agent 对话。

## GREEN：桌面应用检查

**测试输入**：另一段视频联调材料同时包含普通 SSH 无设备权限、sudo 环境变量丢失、Jupyter 自有内核占用，以及两次 `Memory reserve reached`。

**最终收束材料时参与人机协同的执行 Agent 应用结果**：

- 按第 0 层先区分 UID、组、sudo 环境和既有内核，不再把 `No Devices Found` 直接归因于摄像头或 XRT；
- 按 CMA before／during／after 检查，保留缓存回收前后的数值，拒绝由单个空闲值推断泄漏；
- 在视频启动前资源不足时停止后续性能解释，避免把 `frames=0` 写成推理或视频测试失败；
- 对内核只处理已确认属于当前测试的 session，不执行全局清理。

**结论**：`PASS_WITH_NOTES`，Skill 能覆盖这组权限／CMA 案例并避免错误归因。该检查由最终收束材料时参与人机协同的执行 Agent 基于冻结材料完成，不是独立 Agent 压力测试，也没有新增板测。

## REFACTOR：修订与未覆盖范围

初稿把硬件阶段放在较前位置；应用检查后进一步明确：运行环境和既有内核属于第 0 层，未通过时不应进入 Overlay 下载。另补充“短测通过不外推长期无泄漏”。

尚未覆盖 AXI4-Stream 波形级 stall、不同 PYNQ 主版本和长期连续运行；遇到这些问题需扩展协议证据，不能直接套用本案例结论。
