# 智能体工程协作与交接：来源与演进

## 形成来源

本 Skill 由三类材料收束形成：

1. 项目早期大模型辅助 FPGA 研发工作流调研中的任务包、Plan／Act、权限矩阵、分层验证、有界重试和人工审批设计；
2. 历史工程交接文档中实际存在的范围冻结、失败保留、证据索引、未验证边界和后续负责人事项；
3. 最终收束材料时的人机协同记录中的真实人工反馈和目录权限实践。

因此，本文件是**最终收束材料阶段形成的可执行新 Skill**。早期调研不是“项目已经完整运行该工作流”的证明；历史交接材料也不能反推出当时每一条提示词或独立验证者角色。

## 默认轻量协作

推荐“确定性工程流水线＋一个主执行 Agent＋按需独立审查＋人工审批”。并行检索或隔离探索只有在任务可分割、接口稳定且收益大于协调成本时使用。紧耦合 FPGA 任务共享时钟、复位、数据布局和硬件状态，不宜为展示多 Agent 而并行写主线。

## 交接与 Skill 的分工

- 工作流材料说明人、Agent、工具和审查者怎样合作。
- 技术 Skill 说明某类任务怎样执行和验证。
- 任务包把一次具体工作目标、权限和验收绑定到相关 Skill。
- 协作案例保存可观察的提示、反馈、修正和证据，不记录模型内部思维过程。

## 最终收束材料时的人机协同记录中的实际权限示例

用户指定所有新增 Markdown 只能写入原整理工作目录（交付材料现位于 `skill/` 与 `report/collaboration/`），并要求持续做到可提交。最终收束材料时参与人机协同的执行 Agent 据此限制写入范围，在技术事实不清时保留问题，不使用子 Agent，不把最终收束材料时的桌面回放冒充独立审查。

## 来源与外部归属

早期调研参考 SWE-agent 的 ACI、MetaGPT／ChatDev 的结构化交接、Cline 的 Plan／Act、Aider 的差分／测试、OpenHands 的隔离执行和多智能体失败研究。这里只迁移通用原则并独立改写，不声称复现上述系统，也不主张 Plan／Act、人工审批或任务包概念为团队原创。

详细设计依据为项目早期调研 `support.md`；最终收束材料时的人机协同案例见 [Skill 设计纠正](../../report/collaboration/cases/case-01-skill-design-correction.md)。
